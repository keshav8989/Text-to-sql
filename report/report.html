03Problem Statement & Gaps Identified

Our guide asked us to study existing Text-to-SQL research and then solve two major problems found in it. We reviewed the four papers above and noted the same weaknesses coming up again and again. All four depend heavily on very large LLMs, which is expensive. Data efficiency and generalisation to unseen schemas are limited. RL training (Reward-SQL) is unstable. Two problems stood out as the most important and also feasible for us:

Problem 1: Weak schema linking (mid-sem)

Models fail when a question uses synonyms or paraphrases instead of the actual table/column names ("pupils" for student, "earn" for salary). Reward-SQL's error analysis lists wrong table/column selection as a leading error type. SL-prompting fixes this only partly, and it costs extra GPT-4 calls.

Problem 2: No runtime self-correction (end-sem)

None of the four systems repairs its own SQL at inference time. Once a query has been produced, any error, empty result or wrong join is silent. Reward-SQL uses execution feedback only while training, not while answering.

Mid-sem scope: Problem 1 is designed, implemented and evaluated as a working web system (Sections 04–06). Problem 2 is designed and scheduled for the end-semester evaluation (Section 07).

04Overall System Architecture

05Work Completed: Graph-Based Schema Linking

(a) Schema graph. The database is modelled as a graph G=(V,E). Nodes V are tables and columns. Edges E join each table to its columns (weight 0.5) and each foreign key to its primary key (weight 0.8). Every node carries a small synonym lexicon (e.g. student: pupil, learner, scholar; salary: pay, earn, income). Every text column also stores its distinct cell values, so "Computer Science" can be linked to department.dept_name.

(b) Seed scoring. The question is split into 1–3-gram phrases with light stemming. Each node gets the best score among: exact name match (1.0), synonym match (0.9), whole-word containment (0.7), character-trigram Jaccard similarity > 0.45 (×0.8, catches typos and morphology), and cell-value match (0.95). Each match is stored as evidence, which the UI shows to explain the result.

(c) Graph propagation. Two rounds of max-product message passing: s(v) ← max(s(v), wuv·s(u)). Column→table messages are strong (0.85) and table→column messages weak (0.15). This way a matched column pulls in its table without lighting up every column of that table.

(d) Join-path bridging. Tables scoring ≥ 0.42 are selected. A greedy Steiner-tree step then keeps attaching the closest unconnected table using BFS over FK edges, preferring tables already selected. This adds bridge tables the question never mentions, e.g. enrollment in "students registered in Machine Learning".

(e) Pruned prompting. Only the linked tables (with keys) are written as CREATE TABLE DDL. Comments listing the relevant columns and join paths are added. The LLM is asked for a single SQLite query at temperature 0. With linking on, the prompt is about 40–60% shorter than with the full schema, which makes calls cheaper and leaves fewer distracting tables.

(f) Web application. React + TypeScript. Features: a query console, a live linker trace (scores and evidence), an animated schema-graph view, editable SQL, in-browser SQLite execution on a 5-table College ERP database (department, student, instructor, course, enrollment), and a linking ON/OFF switch for ablation. The API key is entered in a Settings dialog in the website itself, so nobody has to edit the code. It is stored only in the browser.

07Planned for End-Sem: SQL Self-Correction via Execution Feedback

  • Error detection: syntax/runtime errors, empty results where rows are expected, type mismatches, and missing joins (Cartesian-product blow-up).
  • Fixer: few-shot LLM prompt, and then a small fine-tuned seq2seq model that takes (question, pruned schema, bad SQL, error message) and returns corrected SQL, for up to k = 3 rounds.
  • Training data: synthetic bad-SQL/fix pairs made by mutating Spider gold queries (drop a JOIN, swap a column, wrong aggregate, flipped operator).
  • Guard: the linker's schema set limits which edits the fixer may make, so fixes don't drift from what the user asked.
